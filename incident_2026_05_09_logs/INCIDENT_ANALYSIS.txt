----------------------------------------------------------------
KEY FINDINGS
----------------------------------------------------------------

1. The autopilot DID receive your Land button presses. Three "land" goals
   were accepted in <2 s, each one entered "Position based land mode."
   The autopilot was not ignoring you.

2. ~5 seconds after the third Land, the autopilot stopped receiving
   position/velocity data from PX4 ("No position or velocity data received!").
   This is the smoking gun. After this point the position controller
   was running on stale state — it did not know where the drone was.

3. Position data loss most likely means one of:
     a) MicroXRCEAgent / DDS link to PX4 dropped,
     b) PX4 entered a mode that stops streaming vehicle_local_position
        (e.g. its own RTL/LAND failsafe took over from offboard),
     c) PX4 disarmed/crashed internally.
   The .ulg from the SD card is needed to discriminate.

4. ROOT CAUSE that turned a glitch into a crash:

   thyra_params.yaml line 58:
       check_position_timeout: false

   The autopilot has a safety branch that triggers a blind-land when
   position data goes stale (main.cpp:589-630). It is GATED by this
   parameter, which is disabled. So when PX4 stopped sending position
   updates, the autopilot kept commanding setpoints based on a frozen
   estimate. There was no failsafe.

   For comparison:
       check_gcs_timeout:      true   ← protected
       check_position_timeout: false  ← NOT protected
       check_geofence:         false  ← NOT protected
       check_battery:          true   ← protected

5. The pre-flight z-origin drifted from 0.04 m (first set_origin of the
   day) to 1.27 m (last set_origin before the crash). 1.27 m is small,
   but it confirms the EKF z-reference was sliding over the session and
   is consistent with running without RTK fix on the rover.

----------------------------------------------------------------
WHY THE DRONE CLIMBED TO ~25 m
----------------------------------------------------------------

The log alone cannot prove this — vehicle_local_position is not in this
log, only autopilot stdout is. But the consistent story is:

  - Set Origin captured a slightly drifted z reference.
  - Takeoff trajectory was generated for ~1.5 m climb.
  - PX4 may have hit one of its own failsafes (GPS quality, mode change,
    or comms) shortly after takeoff. Position stream stopped.
  - Autopilot's position controller, with check_position_timeout=false,
    kept producing setpoints from stale position. With integrators wound
    up and no feedback, it drove thrust hard.
  - PX4, no longer receiving sane offboard setpoints OR no longer in
    offboard mode, behaved according to its own state machine.
  - Drone climbed, hovered, then fell.

This is consistent with the std::min bug at main.cpp:1549 too — that bug
amplifies any positive error in init_state.position.z(). Both effects
likely compounded.

----------------------------------------------------------------
WHAT TO DO BEFORE FLYING AGAIN
----------------------------------------------------------------

(in priority order)

1. Set check_position_timeout: true in thyra_params.yaml. There is
   never a reason to disable this on a real flight. This single change
   would have triggered a safety landing within 0.2 s of position loss.

2. Wait for true RTK Fixed (not survey-in) before flight.

3. Wire an RC kill switch directly to PX4. The ROS stack must not be
   the only abort path.

4. Pull the .ulg from the FC SD card — it has the actual EKF state and
   PX4 mode transitions across the failure.

5. Always run `ros2 bag record` on /asr/thyra/out/drone_state,
   /fmu/out/vehicle_local_position, /fmu/out/vehicle_status,
   /fmu/out/vehicle_gps_position, /asr/thyra/in/drone_command before
   flying. That gives a synchronised picture next time.
